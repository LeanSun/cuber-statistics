## 1. 实测：工程成本

### 1.1 分步计时

| 步骤 | 做什么 | 耗时 | 堆内存 |
|---|---|---|---|
| S0 | 加载 competitions / championships / persons | 0.4s | 120 MB |
| S1 | **流式扫 `results.tsv`（697 万行）** → 决赛名次 + 每人每项目每年的最好成绩 | **12.9s** | 862 MB |
| S2 | 建 (项目 × 年代) 实力池 → 418 个池 / 206.8 万强度条目 | 2.6s | 1192 MB |
| S3 | 逐场决赛算 oppQ → **436,948 条领奖台记录** | 2.5s | 1250 MB |
| S4 | 赛级基线归一 + 聚合到 21,433 名选手 | 0.5s | 1356 MB |
| **合计** | | **18.8s** | **峰值 1.36 GB** |

**单进程、纯 Node、无额外依赖**（只用 `child_process` 调 `unzip -p` 流式解压）。
命令：`node --max-old-space-size=6144 etl/score/m6_strength.js`

> 内存峰值 1.36 GB 看起来高，是因为把 206.8 万个 (选手,项目,年代)→分位的映射
> 全放在内存里。接入 `build.js` 时可以**复用它已有的流式扫描**（`build.js:597` 已经在扫
> results 表），把峰值压到 1 GB 以内。但**没必要现在优化** —— 一次构建跑一次，18.8s 完全可接受。

### 1.2 为什么这么快

- `results.tsv` 虽然 665 MB，但**单趟流式扫描**足够，不需要建索引
- 项目里 `build.js` 已有 `streamTsv()` 基建（`build.js:145`），`unzip -p` + 逐行 split
  就是全部成本
- **关键**：M6 只需要 `round_type_id ∈ {f, c}` 的行（约 44 万条），
  但那 437 万条「非决赛行」也要扫过才知道它们不是 —— 这是唯一的大头（12.9s）

### 1.3 降级方案（如果嫌 1.36 GB 高）

| 档位 | 做法 | 耗时 | 内存 | 与完整版 ρ | Top50 重叠 |
|---|---|---|---|---|---|
| **完整版** | 自建 (项目,年代) 历史分位 + 赛级基线归一 | 18.8s | 1.36 GB | — | — |
| 降级 A | 用 `ranks_single.tsv` 现势排名当强度 | ~8s | ~500 MB | **0.6540** | **23/50** |
| 降级 B | 只在 build.js 已有的 10 条 podiums 内算 | <1s | 几乎为 0 | — | — |

**降级 A 不建议用**，理由见 §2.3 [坑4]：现势排名会把 2015 年的对手按 2026 年的排名评分。
实测完整版 vs 降级 A 的 Top50 只重叠 23 个 —— 榜首从 Stanley Chapel / Kaijun Lin / Max Park
变成 Yiheng Wang / Carter Kucala / Brian Johnson，**这是两种完全不同的评价体系**。

降级 B 可以用，但要接受「只看 10 条领奖台」的样本量限制。

## 2. 实测：真正难的地方 —— 5 个口径坑

这一节是本次实测的主要产出。**每一条都是踩出来的，不是设计出来的。**

### [坑1] `results.tsv` 的 `pos` 不是名次

WCA 导出里 `pos` 的含义是**「该轮次内的卡位」**，`round_type_id` 才是轮次：

| round_type_id | 含义 | pos 实际含义 |
|---|---|---|
| `1` / `2` / `3` | 第 1/2/3 轮 | 该轮内的卡位（**不是最终名次**） |
| `f` | 决赛轮 | 决赛名次 ✅ |
| `c` | 综合轮（少数项目） | 综合名次 ✅ |
| `b` / `h` / `e` / `0` | 其他轮次 | — |

实测 `pos` 最大能到 **912**（333fm 这类无淘汰赛的项目直接上千）。

**反例**：WC2019/333 的 `f` 轮里，Max Park 的 `pos=4`、Philipp Weyer `pos=1` ——
但 Weyer 是 2019 世锦赛三阶**冠军**，Max Park 是季军。
**只看 `f` 轮的 pos 会把名次搞反。** 真正的名次要看「综合该选手所有轮次后的最终排位」。

项目里 `build.js:635` 已有正确判定：`isFinal = rtype === 'f' || rtype === 'c'`。
本脚本沿用。

### [坑2] 分位方向写反

实力池内按「强→弱」排序后：

```
✅ q = 1 - i/(n-1)      i=0 最强 → q = 1.0
❌ q = i/(n-1)          i=0 最强 → q = 0.0
```

第一版我写反了。结果 **Top25 全是「只打过 1 场决赛」的无名选手**：

```
1. 2008WANG05  Shihang Wang          1.0000  n=1
2. 2006SAKA01  Natsuki Sakamoto       1.0000  n=1
3. 2009MANS01  Pablo Mansilla        1.0000  n=1
...
11. 2012WEIB02 Benyuan Wei            0.9970  n=1
```

**Feliks、Max 一个都没进。** 原因很直白：这些人赢的是**弱对手**（在当年同项目池里排末位），
方向一反，"击败弱对手"就变成了最高分。

> 这个坑值得单独强调：它不会报错、不会崩，只会让榜单**看起来很正常但完全颠倒**。
> 属于那种「不交叉验证就发现不了」的 bug。

### [坑3] multi 类项目成绩是编码值

`333mbf` / `333mbo` 的成绩不是数字，是**编码字符串**：

- 旧编码 `1SSAATTTTT`（旧多盲，2006–2011）：`solved = 99 - SS`
- 新编码 `0DDTTTTTMM`：`solved = (99 - DD) + MM`

直接比大小会错乱（比如「未解少」比「未解多」的编码值更大，但成绩更好）。
规则抄自 `build.js:209-228`，本脚本用 `multiScalar()` 折成单调标量 `solved*1e9 - t`。

### [坑4] 时代归一必须自建历史排名，不能用 `ranks_*.tsv`

`ranks_single.tsv` / `ranks_average.tsv` 是**现势快照**（2026-10-15 的世界排名），
**没有时间维度**。用它做对手强度，等于用「2026 年的排名」评价「2015 年的对手」。

实测对照（同一套公式，只换强度来源）：

| | 完整版（自建历史分位） | 降级 A（现势排名） |
|---|---|---|
| ρ(两者) | **0.6540** | — |
| Top50 重叠 | **23 / 50** | — |
| 榜首 | Stanley Chapel、Kaijun Lin、**Max Park**、Bence Barát | Yiheng Wang、Carter Kucala、Max Park |
| 特征 | 跨年代可比 | 「靠当代排名加持」的人被抬高 |

现势版把 **Yiheng Wang（94 条领奖台）、Mark Boyanowski、Rowe Hessler** 这类人顶上来 ——
他们确实强，但**在各自年代他们是第几**被 2026 的现势排名改写了。

> 这正是 M1 的 `f_L`（时代折算）在管的时间维度。如果 M6 用现势排名，
> M1 管时代、M6 管现势，两者在时间口径上直接打架。

### [坑5] 必须做赛级基线归一，否则与 M2 重复计分

`oppQ` 的绝对值天然随赛级上升（实测中位数）：

| 赛级 | 领奖台条数 | oppQ 中位数 |
|---|---|---|
| OP 公开赛 | 402,385 | 0.7284 |
| CC 洲锦标赛 | 33,989 | 0.7409 |
| WC 世锦赛 | 574 | **0.9516** |

如果直接用 `M6 = Σ oppQ × n^-α`，与 M2 的相关系数 **ρ = 0.8497**，
远超旧手册 §5.2 的 0.7 警戒线 —— **等于把 M2 又算了一遍**。

根因：`n^-α` 本身是**次数的函数**，而 M2 也是次数的函数，两者同源。

### 2.1 六种口径的实测对照

这是本次实测最核心的一张表。**同一份数据，只改聚合公式**：

| 口径 | 定义 | ρ(×M2) | Top50∩M2 | 榜单是否合理 |
|---|---|---|---|---|
| E | `ΣoppQ × n^-0.5` | **+0.8497** | — | 合理但**与 M2 重复计分** |
| R | 现势排名口径 `ΣoppR × n^-0.5` | +0.5658 | — | **时代被改写**（坑4） |
| P | 残差，基线=**自己所有记录**均值 | -0.2246 | 3/50 | **过度校正**，丢掉真实强者 |
| Tmean | 残差均值 `Σexcess×w / n` | +0.2137 | 0/50 | 被 n=1 的极端值污染 |
| **T** | **残差，基线=同(项目,年代,赛级)中位** | **-0.0106** | 19/50 | ✅ **正确** |

**口径 P 为什么失败**：把基线取成「选手自己所有记录的均值」，
等于组内 `Σ excess ≡ 0` 恒成立 —— 数学上过度校正，ρ 掉到负数，
Max Park 掉到 965 名、Feliks 掉到 2072 名。

**口径 T 为什么对**：基线取「同 (项目, 年代, **赛级**) 内所有领奖台记录的 oppQ 中位数」，
含义是「**在这个赛级的这个项目里，通常能击败多强的对手**」。
- WC 冠军在 WC 组内不会因为「大家都强」被扣分
- 只有「击败了比该赛级常态**更强**的对手」才加分
- 次数完全不由 M6 负责 → 与 M2 天然解耦

### 2.3 单项目场景（用户明确要求「适合单项目的评价」）

口径 T 分项目聚合后，榜单**非常干净**：

而且每个项目的榜首都不同 —— 说明这一维真的在测「在该项目上击败了谁」，
不是重复 M2 的总量。

### 2.4 与 M2 的正交性

```
M6(口径T) × M2(名次加权领奖台 Σw)  Spearman ρ = -0.0106  (n=9,967, 条数≥5)
Top50 重叠 = 19/50
```

ρ ≈ 0 意味着**完全正交**。对比现有模型里已存在的重复：
「冠军数 × M2 领奖台条数 ρ = 0.84」。

## 3. 最终口径（口径 T）

```
1) 实力池   strength[pid|event|year] = 该选手在 (项目,年代) 池内
             按当年最好单次成绩的排名分位（强→弱排序，q = 1 - i/(n-1)）

2) 对手强度 oppQ(r) = 记录 r 中「被击败的对手」在同(项目,年代)池内的分位均值

3) 赛级基线 base(cell) = 同 (项目, 年代, 赛级) 内所有领奖台记录 oppQ 的中位数

4) 超额     excess(r) = oppQ(r) - base(cell(r))

5) M6_i     = Σ_r excess(r) × w(r)      w = 冠军 1 / 亚军 0.6 / 季军 0.4
```

**聚合不乘任何 `n^±α`** —— 次数由 M2 负责，M6 只管质量。这是与 M2 解耦的关键。

**与 M1 的关系**：M6 是**绝对量纲**（可跨项目比较），
M1 是**相对量纲**（`r = G/G_ref`，已按 (项目,轨道,级别) 归一）。
两者都含时代因子但不冲突：M1 的 `f_L` 管「这段纪录本身跨不跨时代可比」，
M6 的实力池管「这个对手在**当时**有多强」。

## 4. 接入建议

### 4.1 推荐路径

**先做单项目版**（`Tev` 已算好，21 个项目各自一份），理由：
1. 用户明确要「适合单项目的评价」
2. 单项目版**天然规避**了跨项目量纲问题（不需要解释「2x2 的强度和 4x4 怎么加总」）
3. 全局版可作为后续扩展

### 4.2 接入点

`build.js` 已有 `streamTsv()` 和 results 流式扫描（`build.js:597`），
M6 可以**合并进同一次扫描**：

| 步骤 | 现在 | 接入 M6 后 |
|---|---|---|
| S1 扫 results | 已扫（取 podiums / records / evStat） | 同一趟里多抽两项：决赛全名单 + (pid,event,year) 最好成绩 |
| S2 实力池 | — | 新增，约 2.6s / +330 MB |
| S3 oppQ | — | 新增，约 2.5s |
| S4 聚合 | — | 新增，约 0.5s |

**净增成本估计：+5.6s / +400 MB**，总构建时间影响可忽略。

### 4.3 落地前必须做的三件事

1. **交叉验证**：M6 全局榜 Top20 与「公认历史强者」人工核对（已完成，见 §2.2）
2. **与 M1/M2 的相关系数写进断言**：`ρ(M6, M2) < 0.3` 应作为回归断言锁定，
   防止后续改动把口径改坏
3. **multi 类项目单测**：333mbf/333mbo 的 `multiScalar()` 解码要与 `build.js` 的
   `fmtVal()` 对拍（同样输入必须同样输出）

## 6. 结论对用户原始问题的回答

> **「M6 做强度的话，统计起来会很难吧」**

**统计本身不难** —— 18.8 秒、1.36 GB、单进程、纯 Node，一次扫完 697 万行。

**难的是定口径** —— 我实测了 6 种聚合方式，与 M2 的 ρ 从 -0.22 飘到 +0.85，
其中 4 种会产出「看起来正常但完全错误」的榜单（无名选手霸榜 / Max Park 掉到 965 名）。
真正的坑有 5 个：`pos` 不是名次、分位方向反、multi 编码值、现势排名改写历史、赛级基线缺失。

**建议**：按口径 T 做，**优先上单项目版**。它的 Top3 名单
（3x3: Yiheng Wang / Max Park / Tymon；3x3OH: Max Park / Zakrzewski / Karpiński；
4x4: Weyer / Tymon / Akkersdijk）本身就是这一维有效性的最好证明。
